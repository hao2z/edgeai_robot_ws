# RViz导航状态与图例

右侧面板顶部显示协调任务。双机模式分别用相同字段显示两台车的状态、剩余路径、累计到点、最近目标和恢复证据；导航未启动的机器人2明确显示待命。完整的控制器/规划器配置、指令链、传感器和时序放在详情折叠区。单机模式保留完整主面板。最近导航警告附墙钟年龄，只作为诊断线索，不认定根因。顶部控制按钮和 RViz 手动选点控制机器人1。

双机显示树分为 Robot 1 / Robot 2，地图、目标估计和前沿共享。机器人1为绿色全局路径、粉色局部轨迹、黄色局部轮廓；机器人2为橙色全局路径、紫色局部轨迹、浅蓝色目标及局部轮廓、蓝色雷达。两组代价地图默认隐藏，可单独开启。当前双机仿真仅机器人1启用 RGB-D，机器人2不创建空相机显示。两车真值分别来自各自的桥接诊断，只用于比较。

`正在跟踪路径`来自新鲜仲裁状态，不能用屏幕上仍保留的路径判断。`路径跟踪停滞`要求活动任务、跟踪状态及新鲜里程计连续5仿真秒低速；阈值是显示提示，不改变导航和恢复。`RPP控制计算受阻`来自当前RPP诊断的BLOCKED报告，不等于物理接触。

恢复区分动作执行、动作失败、位移证据和导航恢复；动作成功不能直接显示脱困成功。深度区分配置关闭、开启但无新数据、数据新鲜。已标记障碍不会因为点云断流自动清除。

图例默认展开，解释轨迹、目标、两种包络、雷达、深度和代价图。青色深度点包含清障用地面点，不全是障碍。橙色箭头始终表示最近派发目标，任务结束后可能仍保留。黄色RPP前视点不是全局目标。雷达改为固定红色，与图例一致。

数据频率表、同刻TF错误和定位锚点修正放在详情折叠区。锚点修正不是定位误差。诊断按2Hz墙钟刷新，仿真暂停时仍报告时钟未推进；消息年龄和频率主要按仿真时间，另用墙钟检查断流。共享 map_server 激活后，两车都按静态地图解释地图年龄，不要求静态地图持续重发；传感器、代价地图和TF仍检查时效。

只读实现：`scripts/ros/navigation_diagnostics.py`采集，`navigation_status.py`组织显示，`src/edgeai_navigation_rviz/src/navigation_panel.cpp`呈现。两车分别读取会话根目录和`robot2/`内的`nav2-runtime.yaml`，显示的控制器/规划器来自到点策略与该配置，不声称证明插件正在执行。诊断分别写入`alignment.jsonl`和`alignment-robot2.jsonl`，不发速度、目标或参数修改。

终端由`scripts/ros/stream_session_logs.py`统一汇总，包含`cooperative-nav.log`。每条导航事件带机器人归属，两台车的目标、到位和恢复分别去重及统计；共享调度事件不强行归属某台车。任务阶段使用中文短句，重复轮询只显示阶段变化，往复反馈及相同告警按15秒限频；长任务每20墙钟秒显示最近已知阶段，这不是存活或持续取得进展的证明。原始输出保留在各源日志及`console.log`；`events.log`为可读事件，`events.jsonl`同时保留机器人、事件名、结构化任务数据和原始证据。`log-summary.json`含两车各自的导航与恢复统计。整轮结果输出后停止阶段进度提示。
