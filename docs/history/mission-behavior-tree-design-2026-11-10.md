# 集中任务协调与行为树重构：模块、行为、任务和异常清单

整理：2026-11-09；实施更新：2026-11-10。核对基线：`261dc0d`。本文是完整设计与实施清单，非全部已实现。当前已建立独立 `edgeai_mission` 包、固定协调树和S1/C1任务Action/单位编排树，见 [实施状态](mission-refactor-status-2026-11-10.md)。

**后续职责修订优先于下文早期设计**：协调器决定调用哪个任务；任务执行节点持有自身行为树和任务条件检查，向协调器返回反馈/结果。连续计时器属于任务，协调器不重复判定。下文“只在协调节点判定”等早期条目不再限定协调器进程，当前边界以实施记录为准。

目标：一个部署在robot1上的任务协调节点，统一检查、调度、发布、取消和记录任务；两台机器人运行相同的执行行为树。任务流程、动作顺序、重试与恢复分支都能在树中找到。算法、感知和实时控制仍由专门模块完成，不把每个计算步骤写成XML。

## 1. 比赛边界：必须区分两种运行模式

直接核对 [中期任务原文](../competition/KTH_EdgeAI_Midterm_Check_Task_Description.docx) 第1、4、5、7节后，定义以下模式。它们共享行为与调度机制，入口条件不同。

| 模式 | 地图和目标来源 | 起点及流程 | 用途 |
|---|---|---|---|
| `midterm_part1` | 新建SLAM地图；只接受本轮相机识别证据 | 至少一机从起始区自主探索；记录S1/C1，保存地图 | 正式探索识别演示 |
| `midterm_part2` | 队伍预建地图；允许使用文档给定目标坐标 | **两机均从左下起始区开始**，定位后自主分配并完成S1/C1；不依赖Part 1成功 | 正式救援演示 |
| `integrated` | 本轮建图和视觉目标，必要时继续搜寻 | robot1建图/S1后交接地图，再两机执行C1 | 保留当前端到端联调；不能替代Part 2起点核验 |
| `navigation_test` / `cooperative_test` | 可用仿真真值地图或给定目标 | 手动选点/直接C1，明确标记诊断模式 | 调试，不计作自主比赛验收 |

共享13分钟任务计时从Part 1探索开始，包含切换；另有2分钟核验。原文明确10秒停留采用仿真时间，未明确13分钟采用墙钟还是仿真钟：暂按墙钟执行预算，同时记录两种时钟，保留可配置口径。约6/7分钟是建议分配，不是各自硬时限。Part 1不得保留旧地图、目标和探索状态；启动软件可在计时前完成。Part 2应允许操作员选择预定义模式、确认已复位起点，之后自主执行，不允许实时手动选下一导航点。

| 要求 | 判定基准 | 工程附加条件，须与比赛要求分开记录 |
|---|---|---|
| S1 | ID1，中心(1.0,4.1)，至少一机base_footprint水平距离≤0.5m，连续10仿真秒 | 数据有效、低速停车；最终朝向可选，**原文不要求朝向** |
| C1 | ID2，中心(4.1,1.0)，两机水平距离同时≤0.7m，连续10仿真秒；不必同时到达 | 两机定位有效、停车；不增加必须面向标记的比赛条件 |
| 计时中断 | 任一必需机器人出圈，连续计时重置 | TF/定位失效、时间回拨、采样缺口、目标版本变化时也不累计未验证时段 |
| 识别证据 | DICT_4X4_50，ID、类型、视觉相对位置、检测时刻 | 多帧确认、法线、疑似候选是工程机制，不能把疑似物体当成已识别ID |
| 几何与碰撞 | 目标参考为支架下方地面点；避免机器人、墙、障碍和支架碰撞 | 目标偏移点不是救援中心，清图不能清除真实障碍；真值只用于诊断/核验 |

当前S1代码附带朝向判定、C1没有相同要求。重构时应显式拆开 `competition_condition` 与 `execution_constraints`，保留联调兼容配置，但正式半径判定不强制朝向。

## 2. 成熟开源基础模块与自定义边界

下表的“采用”是设计建议；仅“已有”表示仓库或当前环境已经接入。官方库提供执行机制，不会自动实现本比赛的救援与双机调度。

| 基础能力 | 开源方案与用途 | 采用方式及仍需实现的部分 |
|---|---|---|
| 行为树运行时 | **BehaviorTree.CPP 4**：子树、端口、黑板、条件/控制节点、异步节点 | 已有；新协调节点优先C++，复用同一运行时；业务逻辑留在明确子树中。[异步节点说明](https://www.behaviortree.dev/docs/guides/asynchronous_nodes/) |
| ROS行为树适配 | **BehaviorTree.ROS2**：Action/Service/Topic包装及TreeExecutionServer | 首选评估，减少重复通信代码；需要验证安装版本的取消与重发语义，不承诺直接兼容。[上游](https://github.com/BehaviorTree/BehaviorTree.ROS2) |
| 单次导航执行树 | **Nav2 BT Navigator / nav2_behavior_tree**：导航Action、规划/控制/恢复节点 | 已有；保留底层Nav2执行树。上层调用导航Action，不复制控制循环。[Jazzy文档](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/configuring_bt_navigator/) |
| 自定义执行接口 | Nav2 `BehaviorTreeNavigator`插件接口，或独立ROS树执行服务器 | 两种均有现成扩展方式；优先独立小型机器人行为执行节点，内部委托已有Nav2，避免把非导航比赛任务塞进导航器。[官方插件教程](https://docs.nav2.org/jazzy/tutorials/plugin_tutorials/writing_new_navigator_plugin/) |
| 长动作通信 | **ROS 2 Action / rclcpp_action**：接单、反馈、终态、取消 | 已有；统一任务ID、结构化失败、取消确认。接单不等于执行成功，取消请求不等于已经停车。[Nav2 Action定义](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_msgs/action/NavigateToPose.action) |
| 全局路径与局部控制 | **Smac Lattice、RPP、Rotation Shim**；DWB/MPPI保留对照 | 已有；此次不换规划/控制器，统一单机恢复；朝向、倒车、容差显式成为请求策略 |
| 短运动与恢复 | **Nav2 Behavior Server**的Spin、BackUp、DriveOnHeading，以及清图服务 | 已有；通用恢复由同一子树控制。自定义SelectRecovery/OccupiedEscape先保留，后续独立验证。[官方行为服务器](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/configuring_behavior_server/) |
| 节点生命周期 | **ROS lifecycle + Nav2 Lifecycle Manager**，有序转换与bond监测 | 已有；用于地图交接/定位启动，但不等价于协调节点租约或网络分区保护。[官方说明](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/configuring_lifecycle_manager/) |
| 建图与静态定位 | **slam_toolbox、Nav2 map_server/map_saver、AMCL、tf2** | 已有；项目负责地图版本、地标锚点、切换顺序、双机质量检查。[slam_toolbox](https://github.com/SteveMacenski/slam_toolbox) |
| 前沿候选 | 已接入的 **frontier_exploration_ros2** 及其C++核心 | 复用候选提取/收益算法；改成计算候选，由树派发。当前上游节点自己选择和派发目标，**只包装启动/暂停不能算全部决策已入树**。[上游](https://github.com/mertgulerx/frontier_exploration_ros2) |
| 视觉与障碍输入 | 现有OpenCV ArUco、RGB-D几何、Nav2 Obstacle/VoxelLayer、Collision Monitor | 保留为算法/感知/控制服务；对外发布带时刻、来源与质量的数据，不自主创建任务 |
| 候选几何与比赛判定 | 现有 `frustum_search`、`suspect_search`、`rescue_approach`、`cooperative_policy` 等 | 自定义且必要：单位行为薄封装、数学模块可复用；共同停留判定迁到唯一协调节点 |
| 可视化与证据 | BT状态日志、可选Groot2、现有RViz/真值诊断 | 树可视化用于调试，不作为成功判据；任务结果保存判定版本和原始测量摘要 |
| 大规模自动规划 | **PlanSys2**：基于PDDL的任务计划生成 | 暂不引入；当前任务种类和顺序有限，用确定性树和小型候选分配即可。[上游](https://github.com/PlanSys2/ros2_planning_system) |
| 大规模车队交通 | **Open-RMF**：交通计划冲突通知与协商 | 暂不引入；两机先实现有限通行资源和让行。后续多机、多任务时再评估适配成本。[官方FAQ](https://github.com/open-rmf/rmf_ros2/blob/main/docs/faq.md) |

2026-11-09只读核对本机 `/opt/ros/jazzy/share/*/package.xml`：BehaviorTree.CPP **4.10.0**、Nav2相关包 **1.3.13**、slam_toolbox **2.8.5**；`behaviortree_ros2`未安装。BehaviorTree.ROS2上游声明BT.CPP≥4.6及ROS 2 Humble或更新，查到包版本0.3.0；这只是初步适配依据，不能代替编译和取消/重发回归。实现时固定验证过的版本/提交，不升级整个Nav2来迁就包装库。[依赖说明](https://github.com/BehaviorTree/BehaviorTree.ROS2)、[包定义](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.ROS2/humble/behaviortree_ros2/package.xml)。

其通用ExecuteTree接口只有树名、字符串payload/结果/反馈，不提供比赛所需的强类型任务协议。可复用执行服务器，但需定义受控树目录、输入校验及结果适配；不允许通过任意XML或字符串脚本跨机器人执行未登记行为。[接口源码](https://raw.githubusercontent.com/BehaviorTree/BehaviorTree.ROS2/humble/btcpp_ros2_interfaces/action/ExecuteTree.action)

## 3. 运行部署、唯一职责和数据契约

```text
robot1主机
  mission_coordinator（唯一任务权威；运行Mission树和任务检查）
    ├─ robot1 behavior_executor → 本机Nav2/Behavior Server → 速度链
    └─ robot2 behavior_executor → robot2 Nav2/Behavior Server → 速度链

两机：感知、TF、odom、定位、代价图、行为反馈 → 协调节点状态快照
协调节点：选择/保留任务、分配、发布、取消、最终判定 → 持久化任务记录
```

物理上协调节点只运行在robot1；逻辑上使用 `/mission/...`，执行接口使用可配置机器人命名空间。第一阶段兼容robot1根空间和 `/robot2`，不以重命名全部话题作为迁移前提。所有新Action/Service/BT客户端都接受命名空间，禁止在行为代码里硬编码 `/robot2` 或根端点。

| 组件 | 权限 | 不应承担 |
|---|---|---|
| `mission_coordinator` | 唯一任务列表、目标版本选择、资源预约、派发/取消、S1/C1判定、总预算 | 直接发布运动速度、重写路径搜索、用独立Python循环重新决策 |
| `behavior_executor`（两机同一程序/树） | 执行被接纳的单位行为和子树；持有单机执行槽；反馈动作事实 | 选择全局下一个救援目标、擅自宣布比赛任务成功 |
| 现有 `navigation_authority` | 迁移期继续做单次导航互斥/取消/终态确认；后续可并入本机执行器 | 再定义一套S1/C1流程，或与本机执行器竞争运动所有权 |
| 感知/算法节点 | 发布目标、疑似、地图等原始证据；候选计算只读请求 | 抢占动作、直接派发导航、私自确认任务结束 |
| launch/Shell | 启动/停止进程、参数、桌面和日志 | 根据结果文件启动下一比赛阶段 |

**所有运动入口共用一个本机执行槽。**导航树内部Spin属于其父任务；直接观察Spin、前进修正、让行也必须由执行器持有同一资源。不能只锁NavigateToPose，却让另一进程直接调用Spin。迁移期用同一租约/令牌串接现有仲裁，不新增第二个独立所有者。

建议的业务接口为 `ExecuteBehavior` Action，参数类型设计待实施时冻结：

| 类别 | 必需字段 |
|---|---|
| 关联与幂等 | `mission_id, coordinator_epoch, task_id, attempt_id, robot_id, behavior_id` |
| 输入 | 白名单行为类型；带frame的目标/位姿；`map_version, target_version`；到位条件；朝向/倒车策略；动作预算 |
| 反馈 | 行为树路径和阶段、子Action UUID、剩余距离、数据年龄、恢复状态、进展、收到的取消请求 |
| 结果 | `SUCCEEDED / FAILED / CANCELED`；另记执行状态是否已确认；来源阶段、原始错误码/错误串、归一化原因、尝试历史、最终位姿与停车确认 |
| 未确定状态 | `CANCEL_PENDING / STATE_UNKNOWN`属于执行槽状态，不伪装为已终止的Action结果；资源仍占用，停止派新动作 |

重复 `task_id+attempt_id` 返回既有执行/终态，不重复启动；重新尝试必须新attempt_id。旧epoch反馈只归档，不改新任务状态。ROS Action底层UUID仍保留，业务ID不能替代取消UUID核对。

协调节点维护一份缓存快照：RobotState（位姿/速度/定位质量/健康/任务/心跳）、TargetState（ID/类型/坐标锚点/实际观测时刻/质量/版本/来源）、MapState（版本/frame/生效时刻）、TaskState（条件/依赖/资源/预算/尝试）。回调仅更新证据；树节点基于同一快照决策。ROS黑板是进程内对象，不是跨机器人共享数据库。

## 4. 比赛所需的单位行为

以下名称是**拟建接口**，不是当前已有ROS Action名称。单位行为既包括动作，也包括计算与条件；只有明确副作用的节点能控制执行资源。

| ID / 单位行为 | 输入及前置条件 | 完成定义 / 失败分类 | 复用与运行位置 |
|---|---|---|---|
| B01 `CheckReadiness` | 模式、必需机器人；进程/时钟/传感器/TF | 返回缺失项；未就绪不能派运动 | 协调端条件；生命周期、现有诊断 |
| B02 `ResetRunEvidence` | 新mission；机器人已停车 | 清空本轮SLAM/探索/识别内存，建立新记录；旧文件仅归档 | 协调树生命周期节点；不是只删JSON |
| B03 `CheckPoseQuality` | robot/frame、采样时刻 | 新鲜TF/odom、定位协方差/匹配与稳定性通过 | 协调端纯检查；AMCL/tf2 |
| B04 `ComputeFrontier` | 本轮地图、车位、候选历史 | 候选集或明确“耗尽/暂抑制/无数据” | 复用前沿C++核心；不派目标 |
| B05 `ComputeObservationViews` | 未找到ID、相机模型、疑似/覆盖/地图 | 疑似或视锥观察位，含方向/视线/距离/完整成像检查 | 复用候选几何；无候选不等于目标不存在 |
| B06 `SelectRescuePoses` | 固定目标版本、半径、车身、两机状态 | S1一个或C1两个合规停车位；返回每个拒绝原因 | 复用approach/parking；不可仅检查车身中心 |
| B07 `CheckPath` | robot、位姿、朝向策略、版本 | Nav2路径与代价摘要；明确规划错误 | ComputePathToPose；预检查不保证执行时仍可达 |
| B08 `Navigate` | 执行槽、目标、到位策略、预算 | 导航终态与测量；不报告救援成功 | 每机共用Nav2子树，普通/救援恢复一致 |
| B09 `Rotate` | 角度/观察目的、实时车身扫掠可行 | 旋转结束或目标识别触发树取消；报告实际转角 | Nav2 Spin；必须可取消 |
| B10 `TranslateShort` | 方向、距离/速度、修正/退出原因 | 完成一小步后返回，由树重新检查 | DriveOnHeading/BackUp；不写“直到成功”的内部循环 |
| B11 `RecoverNavigation` | 原始失败、当前局部图、尝试历史 | 执行一次有依据的恢复或返回无可行动作 | SelectRecovery/标准动作/必要时OccupiedEscape；两机同树 |
| B12 `SettleAndHold` | 已接近目标、持续状态反馈 | 停车并保持可观测状态；支持撤销和超时 | 执行端持槽，底盘保持；不是10秒Wait即成功 |
| B13 `CancelAndConfirmStop` | 原任务ID/UUID、取消预算 | 子动作终态、执行槽空闲且速度已停 | 本机执行端；取消失败返回UNKNOWN，不释放资源 |
| B14 `SaveMapSnapshot` | 建图已停运动、版本 | 地图与目标锚点同一快照，写入完成标记 | map_saver与项目版本元数据 |
| B15 `SetLocalizationMode` | 已停车、地图来源、转换计划 | SLAM停发后启动AMCL；每条map→odom单一发布者 | lifecycle服务；转换是可反馈的有界多步子树 |
| B16 `InitializeAndRefinePose` | 粗略初值和地图，质量检查 | 稳定定位通过；必要时一小步旋转，再重新评估 | AMCL/激光匹配；不读取真值初始精确位姿 |
| B17 `CheckRescueCondition` | ID/半径、必需机器人、共同采样时刻 | 更新共同连续计时，返回未满足项或完成 | **只在协调节点**；每机只提供事实 |
| B18 `RefreshTargetEvidence` | 视觉原始观测、地图版本、锚点 | 区分新观测、旧投影与冲突；生成可接受目标版本 | 复用ArUco计算，目标提交权归协调节点 |
| B19 `YieldOrStage` | 冲突区、可达让行位、通行预约 | 让行机退出冲突区域，或返回无让行位 | 复用Navigate，不新增速度控制器 |
| B20 `RecordTaskResult` | 最终判定、轨迹摘要、碰撞证据状态 | 原子写入有版本结果；保持定位/显示供核验 | 协调节点；缺碰撞证据标UNKNOWN而非无碰撞 |

B01/B03/B17是短条件/状态计算，B04/B05/B06可作为异步计算Action或快照内纯函数；都不自行重试导航。B08/B09/B10是有反馈且可取消的长动作。B11/B15/B16/B19是由这些单位节点组成的子树。初期可用受控适配器调用Python数学模块，但不能把整个旧救援状态机原样包成单个节点后宣称迁移完成。

## 5. 行为树拆分与控制语义

建议文件边界：

| 树/子树 | 内容 |
|---|---|
| `mission_midterm_part1.xml` | 清空确认→建图→前沿/观察调度→两ID证据检查→保存 |
| `mission_midterm_part2.xml` | 起始区确认→加载预建地图→两机定位→S1分配→C1分配→核验 |
| `mission_integrated.xml` | 当前建图/S1/地图交接/C1联调顺序；复用相同任务子树 |
| `search_target.xml` | 疑似优先→换观察角→视锥/空间候选→导航→转圈→识别检查 |
| `rescue_single.xml` | 选择机器人/停车位→导航→条件检查→必要修正→连续停留 |
| `rescue_joint.xml` | 原子保留两机→选双位→并发接近/冲突调度→共同停留→结果 |
| `robot_behavior.xml` | 两机一致的导航/观察/短运动/保持/取消执行入口 |
| `navigate_recovery.xml` | 路径复用、重规划、跟踪与通用恢复；目标是否救援不改变恢复入口 |

任务节点不保存第二套隐式阶段循环。恢复、换候选、重定位、让行等分支必须在树上可追踪；计算实现可以隐藏，决策不能隐藏。

- 长动作tick不得阻塞：接单后返回RUNNING，通过后续tick检查结果；`halt()`必须发出取消。树线程不调用阻塞的spin-until-done，不能把现有 `wait()` 循环直接搬入叶节点。官方对异步节点与停止响应的要求见 [BehaviorTree.CPP说明](https://www.behaviortree.dev/docs/guides/asynchronous_nodes/)。
- `Sequence`用于有序步骤；监测条件使用明确的持续守卫。不要让ReactiveSequence反复重新执行已完成的生命周期服务或发出重复目标。
- 双机导航可用Parallel风格控制，但两个导航SUCCESS只是进入联合检查；**两台各自到过一次**不能代替同时满足10秒。先到者进入Hold仍持续监控；一机终止失败时，兄弟分支如何保持/取消由联合子树明确决定，不能直接依赖默认Parallel失败就取消全部。
- 导航恢复、候选更换、任务重做分属三个计数器；所有计数都继承同一绝对截止时间，不能在子树重入时重置总预算。
- 延迟只能服务于明确条件（TF恢复、地图重算、定位收敛、交通预约或比赛停留）。等待有原因、有截止时间、有下一分支，不用无条件Wait掩盖死循环。
- 任务完成/失败后先停车、锁定运动任务，保留AMCL/TF/感知和可视化直至明确结束会话；不自动关闭定位再让Gazebo继续，避免重现RViz冻结。

比赛不规定必须先S1再C1。第一阶段保留S1→C1的确定顺序以便回归；不同时引入任意任务重排序。已有完成S1时C1需要两机，可复用先前执行者；S1锁定结果不因离开S1区域而撤销。

### 6.1 调度方法

采用“固定任务顺序+依赖就绪+资源可用”，**不为任务调度引入评分**，不引入拍卖/PDDL或全局最优调度。导航规划器代价与已有候选几何评分不属于任务调度评分，本轮保留。

1. 先处理停止/急停/控制权撤销；其次处理定位失效、动作终态不确定等阻塞事件；再维持已有联合任务和脱困，最后选择新的任务。低优先级观察不得抢占联合停留或正在执行的导航恢复。
2. 任务就绪须同时满足：依赖、模式、预算、数据版本、机器人健康、定位、传感器、空闲执行槽、目标和资源许可。条件未满足记录具体阻塞项，不能每个tick重发目标。
3. S1默认robot1；其不具备执行条件时再按明确规则考虑robot2。C1使用两机，停车位及分配按固定候选顺序逐个验证，选择第一个满足几何/可达/冲突条件的方案；失败则尝试下一候选。不为任务或机器人分配引入加权评分。已有停车几何模块的内部排序暂时保留为过渡实现，不与上层任务优先级混淆。
4. C1先一次性保留两机，防止一机拿到资源后长期等另一机。停车位、通道等资源按固定顺序获取；资源释放依靠确认的退出/取消，而不是心跳超时就假定区域无人。
5. 识别到相关新疑似时，在当前动作的安全边界调度。保留“完成当前疑似假设的有限换角度，再做视锥候选”的偏好；若真正识别到所需ID，可取消搜索并转救援。检测计算可以并行，运动互斥。
6. 普通任务切换需要旧动作终态确认；健康但无需动作的机器人保持可观测。任务状态建议 `PENDING→READY→RESERVED→RUNNING→SUCCEEDED/FAILED/CANCELED`，另有 `BLOCKED/RECOVERING/CANCEL_PENDING/STATE_UNKNOWN`；调度状态与ROS Action状态分开存储。

### 6.2 双机冲突处理

默认两机一起运动，不把全部协作改成串行导航。检查路径在窄通道/门口/救援区是否竞争同一资源；首版仅对已知瓶颈建立预约，路径相交检测只能作为冲突提示，不宣称是完整时空多机规划。

遇冲突：保持稳定通行顺序（已有预约者优先，其次先进入者，最后按任务ID/robot_id破同分）；另一机导航到已检查的暂驻/让行位。若让行位也不可达，不让两车同时后退试错，退出当前预约并重新选双停车位或返回联合规划失败。无进展计数包括双方速度与距离变化，设置有限让行轮数。先到C1者若挡住另一机，可在救援圈内换位或暂时退出；此时共同停留归零。

## 7. 条件检查、坐标版本与连续时间

### 7.1 共同救援判定

协调节点对每个目标保留一份连续计时器，使用共同采样时刻t；不同机器人各取“最新”却时间不一致时不能直接相加判断。采样必须有可用TF、odom和定位证据，消息接收时间不能替代消息时间戳。可采用当前共同可变换时刻策略，但要同时检查各输入与当前时刻的年龄及速度数据一致性。

`distance_i(t) = hypot(base_footprint_i.x(t)-target.x, base_footprint_i.y(t)-target.y)`。

S1：任一已分配机器人满足半径即可进入停留；C1：两机同一时段均满足才进入共同停留。运动执行层的低速停车阈值、定位质量门槛与比赛距离条件单独记录。新鲜但不在圈内不能被 `valid=true` 掩盖，日志分开报告 `data_valid`、`inside[]`、`stopped[]`、`rule_satisfied`、`hold_elapsed`。

使用仿真时间累计10秒；仿真暂停时不增加，回拨时归零；长采样缺口不得补齐假定连续满足。通信/RPC/取消/心跳使用单调墙钟超时，保证仿真暂停时仍可停止。当前0.5秒新鲜度、低速0.02m/s和0.05rad/s、AMCL门槛等可作为兼容起点，不是比赛硬编码规定，需按实际频率验证。

### 7.2 目标和地图的一致性

- `published_at`只代表发布；`observed_at`才表示真正看到目标。相同旧odom观测随AMCL变换重投影，不是新视觉证据。
- 固定地图中的已确认地标应绑定 `map_version/anchor`。SLAM阶段的历史观测重投影与固定地图阶段的AMCL修正应分别建模；保存地图时同步记录目标来源。不能把“读最新JSON”当成坐标修复算法。
- 真正新观测仍要经过质量、创新量和历史一致性检查；**新的时间戳并不保证新位置正确**。当前odom空间历史融合还可能包含漂移观测，重构必须保留这一待验证项，而不是把时间门槛当成彻底修复。
- 若采用Part 2给定坐标，它属于选定地图的确定目标；明确地图到比赛坐标的变换，不让感知旧估计覆盖给定坐标。目标面板法线可作接近偏好，半径任务在已知中心下不应因缺yaw直接失败。
- 已派发任务使用不可变目标快照。小幅更新供下次选择；显著且经过验证的更新由树取消旧动作、确认结束后替换。更新改变判定中心时重置未完成停留，保留旧版本证据；完成结果只读锁定。

## 8. 可能情况与处理责任矩阵

下表是必测类别，不声称列尽所有物理情况。未知错误也须返回结构化失败和上下文，禁止无限Wait或无限重发。

### 8.1 输入、感知和建图

| 情况 | 单机行为/数据模块 | 协调树决定 |
|---|---|---|
| 时钟或必需TF尚未就绪 | 上报缺失和年龄，不启动运动 | 进入有截止时间的就绪检查，预算/启动条件明确 |
| Part 1残留旧图/目标 | 拒绝以该会话数据继续 | Reset/重新初始化并验证，不能只清结果文件 |
| 有雷达、深度关闭 | 按已声明能力执行 | 不报警为“深度故障”；任务若确需深度，则改候选或报告能力不足 |
| 深度开启但接收0/输出0 | 上报QoS/输入/投影/过期计数 | 不当作“前方无障碍”；停止依赖该输入的行为或允许声明的雷达模式 |
| 静态地图长期没有重发 | 检查生命周期、地图版本及订阅是否拿到快照 | 静态图时间戳不更新本身不算过期；与实时扫描/代价图/TF失效分开判断 |
| 解码到ID但PnP失败 | 保留解码证据与拒绝原因 | 选择进一步观察，不当作地图目标已定位 |
| PnP有效但图像时刻TF缺失 | 保留原时刻观测，不用最新TF冒充 | 有限重取/重观测；不要重跑整个任务 |
| 疑似候选对应已知目标 | 发布关联关系，不重复创建ID | 排除/合并；只有真实识别后才确认目标类型 |
| 疑似法线有正反二义性 | 返回多个带评分假设 | 法线优先、有限尝试相反角度和±70°视角扇面，检查距离和遮挡 |
| 所有前沿暂时抑制 | 返回“暂抑制”及可恢复条件 | 可安排有效观察/其他任务；无合理动作时有界阻塞，不标探索完成 |
| 无前沿但缺目标 | 返回地图探索耗尽 | 转视觉搜寻；搜寻无收益/预算耗尽则报告未完成，不无限回原点 |
| 同时发现S1/C1 | 两类证据都持续发布 | 更新列表；按模式与已有任务选下一步，不同时占用同机 |
| 新疑似在视锥导航途中出现 | 数据模块正常更新 | 无紧急性时完成当前动作，再在边界比较；不因每帧新候选抢占 |

### 8.2 导航、恢复与失败归因

Nav2规划错误须保留来源与原码：202=TF、203=起点越图、204=终点越图、205=起点占据、206=终点占据、207=规划超时、208=无有效路径。具体定义来自 [Jazzy ComputePathToPose接口](https://raw.githubusercontent.com/ros-navigation/navigation2/jazzy/nav2_msgs/action/ComputePathToPose.action)；控制器等其他服务器的错误空间不同，不能只按一个整数跨阶段路由。

| 情况 | 单机共同执行树 | 协调树/任务层 |
|---|---|---|
| 路径暂时失效 | 重新检查地图/路径，有限重规划 | 保留原任务，不立即换目标 |
| TF_ERROR | 暂停计入成功，有限新鲜度恢复检查 | 恢复后仅重试已确认终止动作；持续失效→重定位/任务阻塞 |
| START_OUTSIDE_MAP | 返回frame/坐标/地图版本，不盲目运动 | 检查地图和定位；不靠换终点绕过起点坐标错误 |
| GOAL_OUTSIDE_MAP | 返回不可用目标 | 校验目标版本、地图或候选；换合规停车位 |
| START_OCCUPIED | 保留实时障碍，检查本体与边距；可行时受控退出 | 无安全退出则让行/重定位/失败；不能清静态墙伪造净空 |
| GOAL_OCCUPIED | 清楚区分动态、静态及未知；反馈 | 临时动态阻挡可让行，固定阻挡换停车位；不原点无条件重发 |
| NO_VALID_PATH（208） | 与普通导航同样允许适用的清图/姿态调整/恢复；记录恢复是否真正执行 | 单机恢复耗尽后换候选/交通方案；不永久禁止运动恢复，也不强制每次208都运动 |
| 规划超时 | 返回搜索时长/迭代等可得信息 | 限次重规划/换候选；检查预算，不无限延长 |
| 控制器无有效速度/无进展 | 依据实时车身扫掠选动作，保留历史；恢复后重规划 | 无可行动作时换接近位/让行，明确失败，不仅增加重试次数 |
| 碰撞监测把速度置零 | 反馈控制器/平滑后/最终速度及原因 | 若障碍真实则改动作或让行；若数据过期则修输入，不禁用监测冒充脱困 |
| 疑似实体碰撞/车轮打滑 | 停止当前推进，记录命令与实测不一致；可控退出需验证 | 碰撞证据与保护停车分开记；处理后继续或失败由树决定 |
| 恢复动作被拒绝/执行失败 | 尝试下一个未试可行候选，计数有限 | 耗尽后升级，不能无条件重置恢复历史 |
| 目标朝向导致末端绕行 | 若请求要求朝向，由Shim/明确旋转行为处理 | 半径任务已满足时不得因非必要yaw无限绕行；请求参数化 |
| 导航成功但仍出救援圈 | 导航如实返回成功和最终测量 | 不报告救援成功，更新停车位/短距修正后重检 |

恢复是统一能力，不意味着盲目动作：错误坐标、传感器失效、无净空时选择停止/上报是正确结果。208是搜索无解的结果，不足以单独证明终点错误或发生碰撞。

### 8.3 双机、计时、取消和结束

| 情况 | 必须执行的处理 |
|---|---|
| C1一台先到 | 先到者Hold、持续反馈；另一台继续；共同计时尚未开始 |
| 一台失败，另一台仍运行/已到 | 保留健康者状态；先取消并确认失败侧终态，再换该机位姿；如双位需整体更换，显式取消双方，不依赖Parallel默认halt |
| 一台定位失效 | 共同计时归零；该机停止并重定位，另一机保持或按冲突关系让行 |
| 两机争窄通道/彼此视为障碍 | 协调器预约/让行；局部激光继续保留另一台，不能从导航图过滤机器人 |
| 双停车位无几何解/只有一个可达 | 不派发半套联合任务；尝试另一对/分配、重观测或交通方案，有界后报告失败 |
| 圈内车阻挡另一机 | 圈内换位/让行后重新检查；移动期间不累计共同停留 |
| 任一越界、速度未稳或观测缺口 | 共同计时归零，给出具体原因；不拼接两机分别满足的时间 |
| 仿真暂停/变慢 | 仿真停留不增加；墙钟预算与取消/心跳仍运行；实时率低不等于机器人速度指令异常 |
| 仿真时间回拨/世界重置 | 旧TF/目标/动作和计时失效；暂停派发，创建新epoch或重置会话，拒绝旧结果 |
| 协调节点崩溃或网络失联 | 每机执行器按本地单调墙钟租约停止当前任务；该能力当前未实现，必须补。不能依赖崩溃协调节点发取消 |
| 协调节点重启 | 先查询两机当前UUID/epoch/停车状态，对账后再派任务；不能从空任务表直接重发 |
| 旧反馈晚到/相同请求重发 | 按epoch/task/attempt/UUID过滤和幂等处理；旧完成不得覆盖新任务 |
| 发出目标后接单应答超时 | 视为执行可能已开始，先查询/取消并确认；不能假设“没应答就是没执行”而重新派发 |
| 取消应答到达、终态尚未到达 | 维持CANCEL_PENDING，确认停车后释放槽；超时→STATE_UNKNOWN并阻止新运动 |
| 人工急停/接管 | 停止所有自动分支，保留结果；不得由重试子树自动撤销接管；恢复需显式新授权 |
| 总预算耗尽/任务仅完成一部分 | 停车，保存已完成项和未完成原因；不丢弃已成功S1，不把超时当作完成 |
| 结果写入失败 | 任务状态与存储错误分开，有限重写；不可重复执行10秒停留仅为了生成文件 |
| 任务结束、仿真继续 | AMCL/TF/显示继续更新，旧路径显示为历史或清除；不留下看似实时的冻结图像 |
| 结果估计通过、真值不通过 | 记录为验收差异并追查定位/目标误差，不用真值回灌运行决策；碰撞证据缺失则标未知 |

## 9. 现有代码迁移对照与实施顺序

| 现有位置 | 复用内容 | 从旧位置移出的逻辑 |
|---|---|---|
| `scripts/simulation/run-open-source-exploration.sh` | launch参数生成、日志/桌面/进程管理 | 按结果文件启动S1、等待协作结果和阶段决策→Mission树 |
| `normal_rescue.py` | 可提取的ROS/几何适配、测量计算 | 搜寻、导航重试、换点、末端修正、停留决策→子树与统一判定 |
| `cooperative_rescue.py` | 初值变换、匹配计算、地图交接适配 | 唯一任务列表、两机派发/重试/计时→协调节点及联合树 |
| `goal_policy.py` | 位置/朝向/停车策略选择 | 按rescue标签删除规划恢复入口→取消该隐含差异，以显式参数和共同恢复树替代 |
| `navigation_authority.py` | 互斥、接管、UUID取消确认、状态发布 | 不增加比赛任务决策；逐步适配行为执行槽，避免双仲裁 |
| `observation_scan.py`、`target_research.py`、`scan360.py` | 候选、相机几何、Spin适配 | 自主调度/重复循环/绕过行为执行器直接调用Spin→任务树和统一执行接口 |
| 前沿探索器与补丁 | 候选/收益/历史算法 | 自主派发、抢占和其内部运动逃逸→树可见控制；逐项移出，不能和新树同时派目标 |
| `rescue_policy.py`、`cooperative_policy.py` | 半径/净空/分离等纯算法 | 停留权威统一为协调节点；已存在数学单测继续复用 |
| `frustum_search.py`、`suspect_search.py`、感知节点 | 检测/投影/候选评分与关联 | 若有动作调度则移出；数据发布不需要变成BT节点 |
| 自定义恢复C++、原生Nav2 | 局部几何、尝试历史、路径与运动执行 | 保持两机一致；新增协调器不直接替代这些底层算法 |

建议顺序：

1. **冻结接口与验收**：确认本记录的任务/单位行为/结果协议；保留原入口作对照。固定BT适配依赖，先测试取消、反馈和halt。
2. **统一单机执行**：两命名空间共享树和参数派生；普通/救援只差到位约束。增加直接短动作也受控的执行槽与本地失联停止。
3. **建立唯一协调节点**：先迁入任务状态、数据快照、总预算、救援检查和记录，去掉双重任务权威；树表达简单S1/C1流程。
4. **迁入异常与候选调度**：换停车位、重定位、目标新观测、疑似/视锥、让行、取消终态不确定分支；不保留叶节点内的旧长状态机。
5. **迁入探索与正式模式**：前沿计算与派发解耦，Part 1清空与独立Part 2起始条件落地；最后缩减Shell为启动器。
6. **逐层回归再切默认**：先单机、再双机模拟接口、再图形专项、最后两种比赛演示与integrated完整运行。没有实测证据前不删除原可用路径。
